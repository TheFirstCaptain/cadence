# Feature F-002C: Repository and Persistence Boundary

## Objective

Implement one actor-backed SwiftData store behind focused planning, daily-tracking, and History repository protocols.

## User value

Planning, checkoffs, corrections, and future History operate atomically without exposing persistence details or partial failures to the interface.

## Non-goals

- Building My Day, My Goals, or History screens.
- Enabling cloud synchronization.
- Adding behavior beyond the approved F-002 transaction contract.

## Acceptance notes

- SwiftData models and `ModelContext` remain inside one serialized store boundary.
- Repository protocols return immutable Sendable domain snapshots.
- Transactions enforce one plan per week, normalized Goal-name uniqueness, valid frequencies, one checkoff per Goal and local day, active intervals, ordered carry-forward, and latest-occurrence removal.
- Week-specific Goal snapshots retain stable lineage and prior weeks remain immutable.
- Failed mutations do not expose partially updated state.
- Tests use isolated stores and deterministic clock, calendar, time-zone, and UUID dependencies.

## Clarification notes

This slice implements the persistence and concurrency boundary approved in Decision 003 without adding feature UI.

## Workflow
