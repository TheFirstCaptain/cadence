# Feature F-005D: Historical Corrections

## Objective

Allow guarded correction of past Goal checkoffs and individual iIndulged occurrences from Day detail, including exact temporary Undo for occurrence deletion and immediate summary refresh.

## User value

The user can correct inaccurate personal records without rewriting unrelated history or being judged for the change.

## Non-goals

- Adding iIndulged occurrences to past dates.
- Editing historical Goal definitions, plan structure, or category definitions.
- Persisting temporary Undo across app termination.
- Bulk deletion, destructive reset, or silent correction.

## Acceptance notes

- A past Goal checkoff can be added or removed only when that Goal snapshot was active on the selected date and belongs to that date's week.
- Correction is available only when the selected day is earlier than a freshly captured current local day; current-day mutation remains owned by My Day and future-day mutation is unavailable.
- Historical checkoff correction enforces one checkoff per Goal/day and the clarified effective weekly target.
- History owns guarded mutation operations; the view does not reach through the daily-tracking repository.
- Removing one occurrence uses exact occurrence identity, requires no confirmation, and exposes an accessible temporary Undo action.
- Undo atomically restores the exact occurrence ID, instant, preserved local day, time-zone identifier, UTC offset, category identity, and relevant timestamps.
- If Undo expires or the app terminates, the deletion remains committed.
- Failed deletion or restoration rolls back without exposing partial summary state.
- Successful corrections immediately refresh affected Day, Week, and Month presentation through a shared invalidation contract.
- Stale day/period identity, rapid repeated intents, boundary changes, and concurrent refreshes cannot mutate or display the wrong period.
- Correction language remains concise, neutral, and nonjudgmental.

## Clarification notes

- Occurrence Undo is temporary UI state, not a cross-launch recovery promise.
- Reusing current-day `recordIndulgence` cannot satisfy Undo because it would create a new current occurrence rather than restore the deleted historical record.
- The historical checkoff timestamp/time-zone convention must be decided before approval.
